# 架构说明

这份文档解释「为什么这么写」，而不是复述代码。改代码前建议先读完第 1、5、6 节，那三处是最容易改出事故的地方。

---

## 1. 设计约束

项目的所有取舍都来自这几条现实条件：

| 约束 | 后果 |
| --- | --- |
| 必须在现场离线运行 | 模型和推理引擎打包进 APK；不用云端 OCR；不用需要联网的字体/CDN |
| 目标机型可能是几年前的千元机 | 推理用 CPU 单线程 WASM；720p 取景；模型选 PP-OCRv3 而非 v4/v5 |
| 一次实验连续跑 30 分钟到几小时 | 内存必须恒定；不能把所有帧堆在内存里；要有崩溃恢复 |
| 使用者在做实验，不是在看手机 | 界面单手可操作；屏幕常亮；出错要能自己恢复 |
| 数据要能直接进报告 | 导出的表格带采集元信息、带单位、带图片文件名；趋势图单独出图 |

## 2. 数据流

```
摄像头 (1280×720, 30fps)
   │  drawImage → frameCv（离屏 canvas，复用，不新建）
   ▼
取景框 ROI（四角可拖动，坐标归一化 0~1）
   │
   ├─ 模板已锁定 → 按"屏幕→数字区"比例裁出小图（含 4.5% 外扩做二次确认）
   └─ 未锁定     → det 检测出最多 5 行文字 → 逐行 rec → 选最像读数的一行
   ▼
文本 "5.6" / "5,6" / "56"
   │  autocorrect.candidates()：枚举所有可能值 + 权重
   ▼
候选值 → autocorrect.pickValue(text, 预测值)：按趋势选一个
   ▼
assess()：偏离预测是否超过容差？
   ├─ 否 → 采纳，push 进历史
   └─ 是 → 等新帧再读 2 次 → decide() 三票表决
   ▼
记录 {t, value, unit, score, flag, note, votes}
   ├─ 曲线重绘（断点分段）
   ├─ 超标判定（震动/提示音，8s 节流）
   ├─ 存图队列（串行写 MediaStore）
   └─ 每 3s 写快照到 localStorage
```

## 3. 前端模块

| 文件 | 职责 | 不该放进去的东西 |
| --- | --- | --- |
| `app.js` | 状态机、采集循环、曲线绘制、导出、设置、崩溃恢复 | OCR 数学、DOM 细节（尽量） |
| `ocr.js` | 模型加载、预处理、det/rec 推理、后处理成 `{value,text,score,lines}` | 时序逻辑 |
| `autocorrect.js` | 纯函数：候选枚举、趋势预测、容差、投票 | 任何 DOM / 相机 / 存储访问 |
| `style.css` | 深色主题、三段式布局（取景 / 曲线 / 数据） | — |
| `sw.js` | 仅浏览器版离线缓存；APK 内不使用 | — |

`autocorrect.js` 刻意做成不依赖 DOM 的纯模块，因为它是唯一能被单元测试覆盖的部分（23 项断言，覆盖小数点、逗号、空格、突变、连续噪声等场景）。

## 4. 识别链路

### 4.1 未锁定模板（首次使用 / 换仪器）

`OCR.readScreen()` 走完整 PP-OCRv3 流程：

- **det**：短边缩放到 320、长边不超过 960（都是 32 的倍数），DBNet 输出概率图，阈值 0.3 二值化，候选框平均置信度门槛 0.5，外扩系数 1.6。
- **rec**：每个框单独送 CRNN，输入高固定 48 px、宽上限 640；输出字符序列与置信度。
- **选值**：在所有行里挑最像读数的（纯数字、长度 1–6、不含字母），单位行（ppm/ppb）与状态行会被排除。

为什么必须两步：早期只有 rec，把整块画面压成一行 48 px 高去认，屏幕上同时有数值、单位、Status 时置信度只有 0.29，读数经常串行。

### 4.2 模板锁定（日常使用）

点「学习数字区」后，程序记住"屏幕框 → 数字区"的相对比例，之后每帧：

- 直接按比例裁小图，**跳过 det**（省掉一半以上耗时）；
- 裁两次：原位置 + 外扩 4.5%，两者识别结果一致才算稳定（`agree=2`），否则取置信度高的那个并标 `不一致`。

这是一次用精度换速度的取舍：仪器屏幕布局固定、只有数字在变，位置校准一次可以长期复用。代价是移动手机或换仪器后必须重新学习，否则会一直读到空白区域（表现为"未识别"）。

## 5. 自动校正（`autocorrect.js`）

这是全项目最需要小心的地方。

### 5.1 候选枚举

模型输出的原始文本可能是 `5.6`、`5,6`、`5 6`、`56`、`5。6`。`candidates(text)` 会枚举：

| 来源 | 做法 | 权重惩罚 (ln) |
| --- | --- | --- |
| 原样 | 文本里本来就有小数点 | 0 |
| 去点 | 文本有点，但可能是噪点 | 0.18 |
| 整数 | 文本没有点 | 0.08 |
| 补点 | 纯数字串插入小数点得来 | 0.30 |

"补点"惩罚最高，意味着只有当它与趋势**明显更吻合**时才会被选中。这一条是修 `5.6 → 56` 的关键：老代码用正则删掉逗号再找小数点，`5,6` 必然变成 `56`；新逻辑把 `5.6` 和 `56` 都作为候选，让趋势来裁决。

### 5.2 趋势预测

保留最近 8 个"已采纳"点（无异常标记的），线性外推当前时刻的期望值与变化率。

容差由三部分取最大：

```
tol = max( 0.40 ppm + 3%×量程,  15% 相对值 ) × √(dt / 5s)   // 时间因子上限 2.5
```

含义：绝对容差保底（读数在 0.4 ppm 内的小起伏不打扰）、大量程下按比例放宽、采间隔拉长时容差变大（隔 30 秒的两个点本来就可以差得多）。

### 5.3 三票表决（`decide`）

```
读 1（本帧）→ 偏离 → 读 2、读 3（各等一个新帧，最多 500ms）
三票中两票一致 → 采信该值（即使与预测不符：真实突变不能被算法压住）
三票互不相同   → 取最接近预测的值，flag = "待复核"
```

两条设计原则写死在代码注释里，改代码时不要违背：

1. **只做选择与复核，绝不凭空造数**。所有值都来自模型文本，算法不插值、不猜。
2. **一致性优先于连续性**。真实浓度突变时，三次读数会一致支持新值——算法跟随事实，不跟随惯性。

### 5.4 状态标记

| flag | 含义 | 是否进历史 |
| --- | --- | --- |
| 空 | 正常 | 是 |
| 待复核 | 三票不一致 | 否 |
| 低置信 | rec 置信度 < 0.5 | 否 |
| 不一致 | 模板模式下两次裁剪结果不同 | 否 |
| 未识别 / 无文字 | 没读到数字 | 否 |

只有"无异常标记"的点会进历史参与预测，避免一次错读把后续预测带偏。

## 6. 内存与存储（血泪史）

### 6.1 曾经的崩溃

v1.3 之前，照片打包的实现是：把本次会话所有 JPEG 收集成 Blob → 合成 ZIP（JS 内存里）→ base64 → 过一次 Capacitor 桥。半小时 1 秒间隔约 1800 张，峰值内存上 GB，WebView 直接被系统杀掉。用户看到的现象是"提示保存成功，但没有文件，随后闪退"。

### 6.2 现在的做法

- **单张存图**：写一张、释放一张。`SaveQ` 严格串行（并发上限 1），队列积压超过 40 条说明卡了，直接丢弃并提示。
- **记录里不长期持有 blob**：`rec.blob = null` 在写盘成功后立刻执行，内存占用恒定在一两张图。
- **桥接单次上限 10 MB**（`BRIDGE_MAX_BYTES`）：超过就拒绝并提示，而不是让 WebView 在 base64 编码时 OOM。
- **打包交给原生**：`zipFolder` / `archive` 在 Java 侧用 `ZipOutputStream` 流式读取 MediaStore 里的文件写进 zip，JS 只传文件名和元数据。

### 6.3 写入路径

Android 10+ 走 `MediaStore.Downloads` + `IS_PENDING`（写完才可见，失败要删掉 pending 项，否则会留下 0 字节的残留文件）。Android 9 及以下走 `Environment.getExternalStoragePublicDirectory`。两条路径在 `NativeBridgePlugin` 里分开实现，UI 上无差别。

文件落在 `下载/VOCMonitor/<yyyy-MM-dd>/`。

## 7. 导出

| 方法 | 实现要点 |
| --- | --- |
| CSV | 手写 BOM + CRLF，Excel 打开不乱码；元数据块在前，空行分隔 |
| XLSX | 无第三方库，手写最小 OOXML（`xl/worksheets/sheet1.xml` + `sharedStrings` 省略，用 inlineStr），zip 由 `zipStore` 生成 |
| 趋势图 | 1600×900 canvas 绘制，含限值虚线、超标点、最大/最小标注、七项统计；导出 Excel 时同步存一张 PNG |
| 照片包 | 原生 `zipFolder` 打整个日期目录（跨零点则打根目录） |
| 归档包 | 原生 `archive`：CSV/XLSX/PNG 以 base64 传到原生（总限 8 MB），照片在原生侧流式追加 |

曲线绘制的两个细节：

- **断点分段**：相邻点时间差 > 2.5× 采样间隔就断开，不连直线。否则"中途停了 10 分钟"会被画成一条平滑上升的线，误导读图。
- **刻度算法**：nice number（1/2/2.5/5×10ⁿ）取整，避免出现 `3.7、7.4、11.1` 这种刻度。

## 8. 相机生命周期

安卓 WebView 在切后台时会释放摄像头，但 `MediaStream` 对象仍然存在、`readyState` 可能还报 `live`，`videoWidth` 变成 0。表现就是"回到前台画面黑着，要切一次前后摄像头才恢复"。

v1.5 的处理：

1. `visibilitychange → hidden`：把 `video.srcObject` 置空，等约 100 ms 再 `stop()` 所有轨道（顺序反了会触发 `AbortError`）。
2. `visibilitychange → visible`：检查 `readyState !== 'live' || videoWidth === 0`，满足则重新 `openCamera()`。
3. 打开失败时按 300 ms 退避重试 3 次，专门捕获 `NotReadableError` / `AbortError`（系统还没放开设备）。
4. 同时监听 `track.onended` / `onmute` 与 `pagehide`，作为兜底触发。

## 9. 崩溃恢复

- 每 3 秒（节流）把 `{records（不含 blob）, meta, 设置}` 写进 `localStorage["voc.session.v1"]`。
- 启动时若有快照且 `exported === false`，提示"已恢复上次 N 条记录"。
- 已导出过的会话不恢复，避免用户以为数据丢了又重复采集。

只恢复文字记录，不恢复照片——照片已经单独落在文件系统里，`图片文件` 列留着文件名可以对照。

## 10. 原生桥 API

`NativeBridgePlugin`（`cn.voc.reader`）暴露给网页：

| 方法 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `saveFile` | `{data: base64, name, mime, folder, date?}` | `{path}` | 写进 `下载/<folder>/<date>/`；上限 12 MB（base64 前） |
| `zipFolder` | `{folder, date, name}` | `{name, count, bytes}` | 流式打包整个日期目录 |
| `archive` | `{folder, date, name, extras:[{name,data}]}` | `{name, count, bytes}` | extras 走 base64，总限 8 MB；照片流式追加 |
| `keepAwake` | `{on: bool}` | `{ok}` | 原生 `FLAG_KEEP_SCREEN_ON`，比 Web Wake Lock 稳 |
| `info` | — | `{version, code}` | 版本号走 `PackageManager`（AGP 8 不再生成 BuildConfig） |

桥接层的三条铁律：**单次数据有上限、失败要清理、绝不把整批文件塞进一次调用**。
